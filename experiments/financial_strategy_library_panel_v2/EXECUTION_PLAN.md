# Financial Innovation-Challenge Panel v2 — execution and audit plan

This plan defines the runner that must be implemented under a later execution
lock. The design lock contains no v2 licensed row and no empirical outcome.

## Phase 1: predecision preparation

Validate source-file schemas and stat fingerprints, partition daily rows into
ignored origin-safe local files, and create a terminal status for every one of
the 20 origins. For each origin, serialize the eligibility census, excluded
security reasons, SPY belief cutpoints, profile-support counts, universe order,
and source grammar hash. No postdecision return field is readable in this
phase.

## Phase 2: frozen experimental objects

Construct the focused and broad dockets with exact cutoff ties, the 30-scenario
frontier, three burden vectors, and the 27-capability carrier map. Generate all
32 eight-candidate menus per origin and docket from the registered seed and
non-source candidate pool. Serialize each object canonically and bind every
child hash to its origin record.

Solve and independently check all six registered arms. The budget-matched
frontier-only arm begins at the certified frontier-only exact endpoint and
scans every remaining strategy in its frozen predecision order, adding each
whole strategy that fits the safe-arm budget. Record the realized burden,
budget, unused slack, additions, carried capabilities, and whether it
accidentally recovers full closure.

Choose one candidate per arm and menu using only the frozen capability set and
predecision rank. Hash a predecision seal containing every universe, docket,
menu, arm, certificate, and chosen candidate. Independent verification of that
seal is the authorization to open postdecision outcomes.

## Phase 3: held-out evaluation

Evaluate only each frozen candidate on the registered next-year calendar.
Write a terminal menu record for observed, explicit-delisting-to-cash,
unresolved-return, or structural-unavailable status. Never switch candidates.
Retain every origin, docket, arm, and menu key in the terminal census.

Apply the availability gate before calculating a headline. Compute complete
menu pairs, then origin--docket means, then the registered origin-level
summary. Resample whole origins only for the descriptive bootstrap interval.

## Phase 4: independent audits

The release requires separate readers that do not call the construction or
optimization routines:

1. source-schema, duplicate-key, and point-in-time field-access audit;
2. registry and seed replay audit;
3. exact frontier, closure, burden, comparator-order, and arm-certificate
   audit;
4. challenge generation, frozen-choice, and predecision-seal audit;
5. calendar alignment, delisting, missingness, and availability-gate audit;
6. estimand and bootstrap replay from terminal aggregates;
7. computational stress-block membership and timing-scope audit; and
8. public whitelist and licensed-data boundary audit.

Every audit emits a hash-bound pass/fail certificate. Public promotion and
manuscript generation fail closed unless all required certificates pass.

## Phase 5: release decision

The result can be called the flagship financial experiment only when the
registered availability gate and all independent audits pass. A null or
negative contrast remains flagship evidence if the design gates pass; a failed
availability gate is reported as inconclusive. Structural results can remain
supporting evidence, but neither a failed gate nor a failed audit may be
repaired by changing thresholds, menus, candidates, windows, or estimands.
